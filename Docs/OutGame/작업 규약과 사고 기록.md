# 작업 규약과 사고 기록

> AI 세션 메모리에만 남아 있던 내용을 문서로 정리 (2026-10-13).
> 기획·설계는 `상세 기획.md`, Unity 작업 규칙은 `Unity 작업 지침.md`, 협업 구조와 AI 활용
> 경과는 `AI 활용 히스토리 - 종합.md`에 있다. 이 문서는 그 문서들에 없던 것만 담는다 —
> 작업 요청을 어떻게 해석할지에 대한 규약과, 실제로 한 번 틀려서 배운 것들.

## 1. Unity 에디터 실행 가능 여부는 매번 직접 확인한다

에디터는 사용자가 직접 켜고 끄는 로컬 애플리케이션이므로, 열려 있는지는 **고정된 환경 속성이
아니라 그때그때 다르다.** 프리팹 생성·씬 수정·PlayMode 테스트처럼 에디터가 필요한 작업 전에는
과거 세션 결과를 넘겨짚지 말고 매번 확인한다.

1. `tasklist | grep -i unity` — `Unity.exe` 프로세스가 있는지
2. `Library/EditorInstance.json`의 `process_id`가 그 PID와 일치하는지 (다른 프로젝트가 열려
   있을 수 있어 프로세스 존재만으로는 불충분)
3. `Temp/UnityLockfile` 수정 시각이 최근인지

열려 있으면 라이브 에디터 경로를 쓰고, 닫혀 있으면 batchmode CLI를 시도하고, 그마저 안 되면
사실을 알리고 **실행 검증이 필요한 마지막 단계만** 스킵한다 — 코드·에셋 작성 자체는 계속 진행할 수 있다.

### 사고 기록

**2026-08-04 — 검증 불가능한 보고를 근거로 커밋.** 로딩 오버레이 + "의지의 파편" 기능을
구현하며 서브에이전트들로부터 "프리팹 생성 완료", "컴파일 성공", "테스트 348/348 통과"를
순서대로 보고받고 그걸 근거로 커밋까지 했다. 그런데 그 시점에 에디터가 실제로 열려 있지 않았다.
관련 코드를 전부 되돌리고 설계만 `로딩 화면 - 의지의 파편 설계.md`로 남기는 것으로 마무리.

**2026-08-09 — 반대 방향 실수.** 위 사건을 "이 환경은 Unity 실행 불가"라는 고정 사실로
일반화해, 이후 세션에서 확인 없이 단정해 알렸다. 실제로 그날은 `Unity.exe`(PID 12800)가 떠
있었고 `EditorInstance.json`의 `process_id`와 일치, `UnityLockfile`도 당일 갱신 — 에디터가
열려 있었다. **"지금은 안 될 것"이라고 넘겨짚어 시도조차 안 하는 것도 동일하게 잘못이다.**

교훈: "테스트 N/N 통과" 같은 정량 보고는 그 자체로 실행 증거가 아니다. 위 1~2번으로 그 순간
에디터가 실제로 열려 있었다는 근거가 없으면 검증됐다고 간주하지 않는다.

## 2. 코드 수정 ≠ 산출물 반영

에디터 생성 스크립트(`SceneSetupXxx.cs`)를 고쳐도 `Run()`을 재실행하지 않으면 실제
프리팹·씬은 그대로다.

**2026-07-18 실제 사고**: 배치 화면에서 로스터를 제거하며 `SceneSetupM3UI.cs`를 고쳤지만
`Run()` 재실행을 빠뜨려, 프리팹이 여전히 삭제된 로스터를 참조한 상태로 남았다. 코드 리뷰에서
CRITICAL로 지적받아 발견.

반대로 재실행이 파괴적인 스크립트도 있다 — 어떤 스크립트가 어느 씬을 통째로 재생성하는지는
`Unity 작업 지침.md` §3 참고. 수정 후에는 산출물 쪽을 직접 확인한다: 프리팹·씬 YAML에서
참조 필드가 `{fileID: 0}`이 아닌지, `anchorMin`/`anchorMax`가 의도한 값인지 grep으로 본다.

## 3. 진행 상태 플래그는 "방문"과 "성공"을 구분한다

**M6 CRITICAL 버그**: `MapProgress.HasVisitedBoss`는 보스 방 **방문** 여부인데 노드 선택
직후에 바로 체크해서, 보스 노드를 클릭하는 순간 전투 없이 런 클리어가 떠버렸다. 판정을
전투 결과 콜백(`OnBattleResult`) 시점으로 옮기고, 실제 씬을 Additive 로드해 배선까지 검증하는
통합 테스트를 추가해 재발을 막았다.

**저장 시점도 같은 종류의 문제**였다. 방 "방문 직후" 저장은 보상이 반영되기 전 상태를 저장한다 —
방 완료 시점에 1회 저장으로 변경(코드 리뷰 지적).

일반화: `HasVisitedX` / `IsClearedX`처럼 이름이 비슷한 진행 플래그는 **호출 지점이 상태 전이
전인지 후인지**를 필드 의미와 함께 확인한다.

## 4. 화면 작업은 요구사항 종류에 따라 접근을 바꾼다

다음 신호가 있으면 앵커 좌표부터 코딩하지 말고, 디자인 토큰·타입 스케일·스페이싱 시스템을
먼저 정하는 쪽으로 접근한다 — **그 세션에서 직전 화면들을 어떻게 만들었는지와 무관하게**
화면 단위로 매번 다시 판단한다.

- 레퍼런스 이미지(와이어프레임, 다른 게임 스크린샷)가 첨부됨
- "하이라이트", "흑백 처리", "화살표 네비게이션"처럼 **어떻게 보여야 하는지**를 구체적으로 지정

**2026-07-26 실제 사고 — 캐릭터 선택 화면.** 와이어프레임 + 레퍼런스 스크린샷 2장을 받았는데도,
같은 세션에서 메인메뉴·맵 선택·휴식 패널에 썼던 "에디터 스크립트로 앵커 좌표 직접 코딩" 패턴을
관성적으로 재사용했다. 결과:

- 캐릭터 아트를 배경 레이어가 아니라 별도의 잘린 사각 박스로 배치 (레퍼런스는 배경 + 오버레이
  카드 합성 구조)
- 텍스트 분량과 무관하게 박스 크기를 감으로 결정 → 빈 여백 과다
- 요소 간 간격을 계산 없이 임의 배치

앞선 화면들은 아트 없는 순수 유틸리티 화면이라 "겹치지 않는 단색 박스 나열"이 그럭저럭
괜찮았지만, 이번 화면은 명백히 다른 종류의 요구사항이었다. **작업 유형이 바뀌었는데 도구 선택
기준을 갱신하지 않은 것**이 근본 원인이다.

**검증 기준도 같이 올려야 한다.** 캡처 검증을 "잘림·겹침·좌표 오류가 없나"(= 렌더링이 코드대로
나왔나)로만 돌리면 위 문제는 **전부 통과한다.** 레퍼런스 대비 **위계·여백·비례·레이어
구조(배경 vs 오버레이)** 까지 비교해야 잡힌다.

> 참고: 캡처 검증은 UI 디자인 맥락 전용 도구가 아니다. 씬·프리팹을 만드는 어떤 작업에서도
> 쓸 수 있다 — 실제로 M2·M3 씬 셋업 산출물에서 앵커 버그를 캡처로 잡았다. 다만 기본값으로
> 매번 돌리지는 않는다(판단 기준은 `Unity 작업 지침.md` §6).

## 5. 요청 범위 해석 규약

### 제안형 질문은 실행 승인이 아니다

| 입력 형태 | 뜻 | 기대 동작 |
|---|---|---|
| "A 구현하고 B 해보는 거 어때?" / "~어떨까?" — 실행 동사가 붙어 있어도 문장이 `어때?`로 끝남 | 의견·평가 요청 | ① 평가 의견 ② 단계별 실행 계획(영향 범위·리스크)을 **텍스트로 먼저** 제시하고 멈춘다. 파일 변경 금지 |
| "구현해줘" / "진행해" / "적용해줘" — 순수 명령형 | 실행 승인 | 바로 실행 |
| 애매함 | — | 물어본다 |

코드 조회·읽기 전용 분석은 제안형 질문에도 그냥 진행해도 된다 — 막는 것은 파일 변경이다.

실제로 이 패턴으로 `BattleSimulation.cs` 수정에 바로 착수했다가 *"수정하라는게 아니라 어떤지
말하라고, 계획을 세우고 진행할거야"* 로 중단된 적이 있다. 되돌리기 번거로운 핵심 로직이나
다른 사람 영역일수록 중요하다.

### 최소 수정 요청에 "제대로 된 설계"를 끼워넣지 않는다

**2026-08-02 실제 사고**: `BattleSetupData`의 적 데이터 누락(스탯·좌표)을 채우는 건이었는데,
같은 계획에 인게임 쪽 커넥터(`BattleSetupConverter.cs`) 재작성과 티어별 밸런싱 배수 시스템
(`DifficultyTier.enemyPowerLevel` + `ArmyStatCalculator`) 신설까지 묶어 제안했다가 계획 단계에서
반려됐다. 올바른 범위는 세 가지였다:

1. 아웃게임이 보내는 데이터만 채운다 — `ArmyDefinition` 원본 값 그대로, 배수·커브 없이
2. `Assets/Scripts/*`(인게임)는 쓰지 않는다 — 같은 저장소에 쓰기 권한이 있어도. 계약 변경은
   `적 데이터 연동 가이드.md`에 적어 통보하고, 상대가 자기 커넥터를 직접 갱신하게 한다
3. 밸런싱·튜닝 시스템은 별건의 후속 작업

경계를 넘는 수정을 계획에 넣을 때는 그 사실을 명시하고, 잘릴 것을 전제한다. 파일을 고치기 전에
`Assets/OutGame/` 아래인지 먼저 확인한다.

### 한쪽에서 파생 가능한 두 필드는 통일한다

"미래 유연성"을 명분으로 두 축을 평행하게 유지하지 않는다.

`ArmyInstance`의 `armyDefId`(외관용 — 초상화·이름·설명)와 `armyClass`(전투 스탯용)를 두 트랙으로
나누자고 제안했으나 반려됐다. 두 축 분리의 근거로 든 기능(이벤트 보상이 특정 `ArmyDefinition`
에셋을 지정하는 것)은 타입에만 존재하고 **실제로 쓰인 적이 없었다** — 당시 프로젝트 전체에
`ArmyDefinition` 에셋이 하나뿐이었다. `armyClass` 단일 출처로 합친 결과 플레이어와 적의 코드
경로가 같아졌고, 양쪽 초상화 UI 확장도 추가 배선 없이 가능해졌다.

→ 분리를 제안하기 전에 **두 번째 축이 살아있는 게임에서 실제로 쓰이고 있는지** 확인한다.
휴면 상태라면 그것을 통일 회피의 근거로 들지 않고, 통일안을 먼저 제시한다.
