# 적 데이터 연동 가이드 (인게임 개발자용, 2026-08-02 갱신)

**계약 변경 — 액션 필요, 아직 반영 안 된 것으로 보임**: `EnemyArmy`에 최종 스탯·배치 좌표 필드가
추가됐다(아래 "`EnemyArmy` 필드" 참고). 지금 `Assets/Scripts/Integration/BattleSetupConverter.
AddEnemySquads()`를 다시 확인해보니 여전히 스탯 필드는 채우지 않고("적은 업그레이드·증강이 없어
인게임 .asset 원형값이 곧 최종값" 주석) `ClassToDepth`로 좌표도 자체 계산하는 중이다 — 이제
`EnemyArmy`에 실제 값이 들어오니 **아군과 동일하게(`ToSquadRequest(DeployedArmy)` 참고) 그대로
복사하는 방식으로 바꿔야 한다** — `maxHp = enemy.soldierHealth`, `slotX = enemy.slotX` 등. 이
파일은 인게임 쪽 코드(`Assets/Scripts/Integration/`)라 아웃게임 쪽에서 대신 고치지 않았다.
자세한 내용은 아래 "아군(`DeployedArmy`)과의 차이" 절 참고.

**참고 — 적 데이터를 만드는 방식이 두 차례 더 바뀌었다(인게임이 받는 필드 모양 자체는 안 바뀜)**:
1. 자동 수식으로 적 스탯을 역산하던 방식을 버리고, 개발자가 커스텀 에디터(`EnemyPresetEditorWindow`)로
   직접 만든 "프리셋 조각"(병과·업그레이드·증강을 authored)을 난이도 커브에 맞춰 조합하는 방식으로
   바꿨다. `EnemyArmy.upgradeLevel`은 이제 난이도 커브가 자동으로 매기는 배율이 아니라, 프리셋을
   만들 때 개발자가 직접 고른 값(0~5, 플레이어 부대 업그레이드 단계와 같은 의미)이다.
2. 병과 차이를 표현하던 %보정 시스템(`ClassBalanceConfig`)을 없애고, 병과마다 실제 수치를 담은
   `ArmyDefinition`(army_none/warrior/hunter/assassin/archer 5종)을 직접 쓰도록 바꿨다.

두 변경 다 **`EnemyArmy`가 인게임에 넘기는 필드 셋·의미는 그대로다** — 최종 스탯·좌표가 이미 계산돼
들어온다는 계약 자체는 안 바뀌었으니, 위 액션 아이템(스탯·좌표 그대로 복사) 외에 추가로 할 일은 없다.
정확한 스탯 수치는 계속 플레이테스트로 조율되는 초안값이지만, "배율 없는 원본값"이던 상태는 지났다
(§9 참고).

아웃게임이 전투 시작 시 넘기는 `BattleSetupData`에 **적 진영 구성이 포함되도록 확정**됐다. 이
문서는 그 부분(`enemies`)과, 같이 넘어가는 **플레이어 캐릭터/스킬 선택 정보**, 그리고 양쪽이
공유할 수 있게 된 **씬 이름 상수**를 설명한다. 전체 계약은
[[상세 기획#7. 인게임 인터페이스 (아웃게임 확정안)]] §7을 참고 — 이 문서는 그중 위 세 가지의
사용법만 보충한다.

## 결론부터: `encounterId`로 뭔가 조회할 필요 없다

이전까지는 `BattleSetupData.encounterId`가 "적 구성을 조회하는 키"처럼 문서화돼 있었고, 그 조회를
수행할 `RoomEncounterTable`은 인게임 쪽이 만들 걸로 남겨져 있었다. 하지만 그 테이블은 실제로
만들어진 적이 없고, 같은 역할을 아웃게임의 `EnemyCompositionConfig`가 이미 하고 있었다 —
난이도 커브 카운터 기준으로 적 수·병과 구성·보스 구성을 정하는 로직이다.

**그래서 2026-07-29부터는 아웃게임이 그 결과를 직접 계산해서 `BattleSetupData.enemies`에 실어
보낸다.** 인게임은 이 리스트를 그대로 스폰에 쓰면 되고, `encounterId`는 로그·디버깅용 참고
식별자로만 남아 있다 — 조회 키가 아니다.

## `EnemyArmy` 필드

`Assets/OutGame/Scripts/Logic/Battle/EnemyArmy.cs` (`OutGame.Logic.Battle` 네임스페이스,
Unity 타입 미사용 — 순수 POCO라 인게임 프로젝트에 그대로 복사/참조 가능):

```csharp
public class EnemyArmy
{
    public string armyDefId;    // army_none/warrior/hunter/assassin/archer 중 하나 — armyClass로 자동 결정, 3D 모델/외형 매핑용 참고값
    public ArmyClass armyClass; // None | Archer | Warrior | Hunter | Assassin
    public int soldierCount;    // 스폰할 병사 수

    // 프리셋 제작 시 개발자가 직접 정한 값(0~5) — 플레이어 부대의 업그레이드 단계와 같은 의미.
    // 난이도 커브가 자동으로 매기는 배율이 아니라 authored 값이다(2026-08-02 프리셋 조각 체제).
    public int upgradeLevel;

    // 최종 스탯 — DeployedArmy와 동일한 의미. 위 upgradeLevel과, 병과별로 authored된
    // ArmyDefinition(army_warrior 등) 값이 이미 반영된 것 — 인게임이 재계산할 필요 없이 그대로 쓴다.
    public float generalHealth, generalAttack, generalDefense;
    public float generalCritRate, generalMoveSpeed;
    public float soldierHealth, soldierAttack, soldierDefense;

    // 배치 슬롯 (2026-08-02 추가) — 아웃게임 배치 화면(EnemyFormationAssigner)이 계산한 좌표.
    // 0~1 정규화, DeployedArmy.slotX/slotY와 동일한 의미.
    public int slotId;
    public float slotX;
    public float slotY;
}
```

- `armyDefId`: 병과마다 다른 값(army_none/warrior/hunter/assassin/archer)이다 — 예전엔
  `"army_basic"` 하나뿐이었는데, 병과별로 실제 정의(스탯+장군 이름+초상화)를 authored로 분리하면서
  (2026-08-02) 값도 병과 수만큼 다양해졌다. 스탯 밸런스 계산에는 안 쓰이고, 인게임이 외형/모델을
  고를 때 참고하라고 남겨둔 값이다 — `armyClass`로도 이미 같은 정보를 알 수 있어서, 굳이 이 필드로
  뭔가 새로 매핑해야 할 필요는 없다(참고용일 뿐, 필수 소비 필드 아님).
- `armyClass`: 아군 쪽 `DeployedArmy.armyClass`와 완전히 같은 enum이다. `None`은 "기본(무병과)
  군대"를 뜻한다 — 실제로 존재하는 값이지 누락이 아니다. 값은 None/Archer/Warrior/Hunter/Assassin
  5개뿐이다(예전에 있던 미사용 예약값 Cavalry/Spearman은 2026-08-02에 아예 제거됨).
- `soldierCount`: 그대로 스폰할 병사 수. 아군과 달리 증원/업그레이드/증강 보정이 없는 **순수 기본
  값**이다 — 적은 `RunState`에 저장되는 영구 자산이 아니라 이 전투 1회용으로 그때그때 생성된다.
- 스탯/좌표: 아래 "아군(`DeployedArmy`)과의 차이" 참고.

## 아군(`DeployedArmy`)과의 차이

적 쪽은 아이템 장착, 장군 스킬, 업그레이드 단계, 증강 같은 "선택지"는 없다. 하지만 그 결과로
나온 **최종 스탯과 배치 좌표는 아군과 완전히 같은 방식으로 실려 온다** (2026-08-02부터):

| 아군(`DeployedArmy`) | 적(`EnemyArmy`) |
|---|---|
| `equippedItemId`, `generalSkillId` | 없음 (적은 아이템/장군 스킬 개념 자체가 없음) |
| `generalSkillUpgradeCount` | 없음 (적은 장군 스킬 강화 증강 개념이 없음) |
| `upgradeLevel`(§4-26 업그레이드 단계, 참고용) | **있음** — 값을 얻는 경로만 다름: 플레이어는 재화로 사서 올리고, 적은 프리셋 제작 시 개발자가 직접 정한 값. 의미(0~5, 최종 스탯 배율 계산에 쓰임)는 동일 |
| 최종 스탯(`generalHealth` 등, 배율 이미 반영) | **있음** — 난이도 배율 + 병과 보너스가 반영된 값(정확한 수치는 계속 조율 중, §9), 필드 이름·의미는 동일 |
| `slotId`/`slotX`/`slotY`(아웃게임이 배치 UI에서 결정한 좌표) | **있음** — `EnemyFormationAssigner`가 계산한 값을 그대로 |

정리하면: 아웃게임은 "**어떤 병과가 몇 명씩, 어떤 스탯으로, 어디에** 나오는지"를 전부 확정해서
넘긴다. 인게임은 재계산 없이 그대로 스폰하면 된다 — 아군 쪽과 원칙이 완전히 같아졌다.
`roleId`/`generalId`(어떤 애니메이션·스킬 에셋을 쓸지)만 여전히 `armyClass`에서 인게임이
매핑해서 고른다 — 이건 스탯이 아니라 에셋 선택이라 인게임 소유가 맞다.

## 읽는 예시

```csharp
// 인게임 쪽 전투 씬 부트스트랩 (예시 — 실제 스폰 로직은 인게임 재량)
BattleSetupData setup = BattleBridge.ConsumePendingSetup();
foreach (EnemyArmy enemy in setup.enemies)
{
    // enemy.armyClass로 외형/유닛 프리팹 선택, enemy.soldierCount만큼 스폰.
    // 스탯·좌표는 아웃게임이 계산해서 보낸 값을 그대로 쓴다 — 재계산하지 않는다.
    SpawnEnemyUnit(enemy.armyClass, enemy.soldierCount,
        health: enemy.soldierHealth, attack: enemy.soldierAttack, defense: enemy.soldierDefense,
        slotX: enemy.slotX, slotY: enemy.slotY);
}
```

`setup.enemies`가 비어 있는 경우는 없다 — `DeploymentState.BuildSetup(...)`이 `enemyComposition`
파라미터를 null 검증하고, 전투/보스 방 진입 시 `InGameFlowController.OpenBattleRoom`이 항상 최소
1개 이상의 적 구성을 생성해서 넘긴다.

## 아직 안 넘어오는 것 / 아직 미흡한 것 (§9 미결)

- **적 버프**: 1차는 아웃게임 UI에 "없음"만 표시. 버프 시스템 자체가 아직 설계 전이라 `EnemyArmy`에
  버프 필드가 없다.
- **스탯 밸런싱 수치 자체는 초안값**: `soldierHealth`/`generalAttack` 등은 병과별 `ArmyDefinition`
  (`Assets/OutGame/Resources/OutGame/Data/ArmyDefinition_army_*.asset`, 2026-08-02 개편 — 병과 차이를
  %보정이 아니라 authored 값으로 직접 표현)에 업그레이드 배율(`upgradeLevel`)을 곱해서 계산한다 —
  "배율 없는 원본값"이던 상태는 지났다. 다만 각 병과 정의의 정확한 수치는 플레이 테스트로 계속
  조율할 초안값이다.
- `EnemyCompositionConfig`(난이도 커브 구간별 프리셋 등급 가중치·보스 구성)와 프리셋 조각
  (`EnemyPresetEditorWindow`로 제작) 자체도 여전히 초안값이다.

이 항목들은 데이터 전달 여부의 문제가 아니라 밸런스/설계 협의가 더 필요한 부분이라 별개로
남겨뒀다 — [[상세 기획]] §9 미결 항목 표 참고.

## 플레이어 캐릭터/스킬 정보

`BattleSetupData`에는 적 구성과 별개로 캐릭터 선택 화면(§5.2.5)에서 고른 값도 실려 있다:

```csharp
public string playerCharacterId;      // 고른 캐릭터 id (지금은 char_1~char_4 플레이스홀더)
public string playerCharacterSkillId; // 그 캐릭터의 스킬 id — 런 전체에 걸쳐 캐릭터당 정확히 1개
```

`armies`/`enemies`와 같은 자리에 있고, **전투마다(런 전체에 1번뿐인 값이어도) 매번 다시 실어
보낸다** — 별도의 "런 시작 시 1회 전달" 채널이 없다. 스킬 세부 효과(수치·발동 조건 등)는 아웃게임이
정의하지 않는다 — `DeployedArmy.generalSkillUpgradeCount`와 같은 원칙으로, "어떤 스킬을 골랐는지"만
전달하고 실제 구현은 인게임 몫이다.

**현재 상태(2026-07-29 확인): 이 두 필드는 아직 아무도 안 읽는다.** `PLAYER_SKILLS.md`에 문서화된
플레이어 스킬 4종(번개/독구름/힐 장판/전투 함성)은 어떤 캐릭터를 골랐든 상관없이 항상 전부 다
쓸 수 있게 인게임 자체적으로 구성되어 있고, `BattleSetupConverter.ToBattleRequest(...)`도
`BattleRequest`/`SquadRequest`도 이 값을 옮기지 않는다 — 캐릭터 선택은 지금 전투에 아무 영향이
없다. `PLAYER_SKILLS.md` §7에 인게임 쪽이 먼저 물어둔 대로("메타 진행에 스킬을 얹을 계획이 있으면
알려달라"), 나중에 캐릭터별로 쓸 수 있는 스킬을 제한/해금하는 식으로 연결하고 싶다면:

```csharp
// BattleSetupConverter.ToBattleRequest(...) 안에, 예시
request.playerSkillId = setup.playerCharacterSkillId; // BattleRequest에 필드 추가 필요
```

이 확장이 필요한 시점에 알려주면 아웃게임 쪽에서 계약을 더 바꿀 일은 없다 — 이미 넘어가고 있는
값을 인게임이 받아 쓰기만 하면 된다.

## 씬 이름 상수 (`SceneNames`)

메인메뉴/아웃게임/전투 씬을 오갈 때 양쪽이 각자 문자열 리터럴로 씬 이름을 하드코딩하면 한쪽이
씬 이름을 바꿔도(이번에 실제로 `InGame` → `OutGame`으로 바뀌었다) 조용히 어긋난다. 그래서
아웃게임의 씬 이름 상수 클래스를 인게임도 그대로 참조할 수 있게 옮겨뒀다:

```csharp
// Assets/OutGame/Scripts/Logic/Flow/SceneNames.cs — namespace OutGame.Flow
public static class SceneNames
{
    public const string MainMenu = "MainMenu";
    public const string OutGame = "OutGame";   // 2026-07-29부터: 맵선택/캐릭터선택/방그래프 통합 씬
    public const string Battle = "Battle";     // 인게임 전투 씬
}
```

`OutGame.Logic` 어셈블리 소속이라(2026-07-29 이동) `NHN.Integration`이 이미 참조하고 있는
`OutGame.Logic`을 통해 별도 어셈블리 참조 추가 없이 바로 쓸 수 있다:

```csharp
using OutGame.Flow;
// ...
SceneManager.LoadScene(SceneNames.Battle);
Scene outGameScene = SceneManager.GetSceneByName(SceneNames.OutGame); // 하드코딩 "InGame" 대신
```

특히 `BattleBridgeConnector.cs`의 복귀 대상 씬 이름 상수(`OutGameSceneName = "InGame"`)는 이번
씬 통합으로 실제 씬 이름이 `OutGame`으로 바뀌면서 더 이상 일치하지 않는다 — `SceneNames.OutGame`으로
바꿔 참조하면 이후 아웃게임 쪽에서 씬 이름이 또 바뀌어도 컴파일 타임에 잡힌다(문자열 리터럴이었으면
조용히 실패했을 부분).

## 환경 설정(사운드 볼륨) 공유 (`SoundSettings`)

메인 메뉴의 "이어하기"를 없애고 그 자리를 "환경 설정" 버튼으로 대체했다(2026-07-30). 환경 설정
팝업은 1차로 사운드 볼륨 슬라이더 하나만 있고, 아웃게임(메인 메뉴/OutGame.unity)과 인게임(Battle.unity)
양쪽에서 "같은 볼륨 값"을 공유해야 한다 — 프로젝트 전체에 오디오 믹서/오디오 소스가 아직 하나도
없어서(2026-07-30 기준), 이번엔 값 저장/조회만 공용으로 만들고 실제 UI는 각자 만든다.

```csharp
// Assets/OutGame/Scripts/Logic/Audio/SoundSettings.cs — namespace OutGame.Logic.Audio
public static class SoundSettings
{
    public const string VolumeKey = "OutGame.MasterVolume";
    public const float DefaultVolume = 1f;

    public static float MasterVolume { get; set; } // PlayerPrefs로 영구 저장, 0~1로 클램프
}
```

`SceneNames`와 똑같은 이유로 `OutGame.Logic` 소속이라 `NHN.Integration`이 이미 참조 중인
`OutGame.Logic`을 통해 별도 어셈블리 참조 추가 없이 바로 쓸 수 있다:

```csharp
using OutGame.Logic.Audio;

// 볼륨 슬라이더 값이 바뀔 때
SoundSettings.MasterVolume = sliderValue; // PlayerPrefs에 저장, 0~1로 클램프됨
AudioListener.volume = sliderValue;       // 실제 소리 크기 반영은 호출자 책임 — SoundSettings는 값만 저장한다

// Battle 씬이 시작될 때(플레이어가 메인 메뉴/OutGame을 거치지 않고 Battle.unity를 직접 열 수도 있으므로)
AudioListener.volume = SoundSettings.MasterVolume;
```

주의할 점:
- `AudioListener.volume`은 씬이 아니라 프로세스 전역 정적 값이라 한 번 설정하면 씬을 넘나들어도
  유지된다. 다만 Unity 프로세스를 새로 시작할 때마다(에디터 Play, 빌드 실행 등) 기본값 1로 리셋되므로,
  **본인 쪽 진입 씬(Battle.unity)에서도 한 번은 `AudioListener.volume = SoundSettings.MasterVolume;`를
  호출**해야 한다 — 아웃게임은 `MainMenuController`/`OutGameFlowController`의 `Awake()`에서 이미
  각각 적용하고 있다(둘 중 하나만 거쳐도 되지만, 어느 씬이 먼저 열려도 안전하도록 이중으로 넣어뒀다).
- 실제 볼륨 슬라이더 UI(팝업 프리팹, 레이아웃 등)는 아웃게임 쪽만 만들었다 — 인게임 쪽 환경 설정
  UI는 각자 필요에 맞게 만들고, 값 저장/조회는 위 `SoundSettings.MasterVolume`을 그대로 쓰면 된다.
- 1차는 마스터 볼륨 하나뿐이다. BGM/SFX를 따로 조절할 계획이 생기면 그때 `SoundSettings`에 필드를
  추가하면 되고, 지금 미리 만들어두지 않았다.
