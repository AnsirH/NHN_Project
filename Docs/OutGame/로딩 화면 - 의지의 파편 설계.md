# 로딩 화면 — "의지의 파편" 설계 (미구현, 설계만 확정)

> 2026-08-04 세션에서 실제 구현까지 진행했다가, 현재 세션 환경이 Unity 에디터/테스트 러너를
> 실행할 수 없어(unity-scene-setup·unity-tdd-guide 서브에이전트의 컴파일·테스트 결과를 신뢰할 수
> 없음) 코드를 전부 되돌렸다. 설계 방향 자체는 확정된 상태라 이 문서로 남기고, Unity 에디터
> 접근이 되는 환경에서 이 문서를 그대로 구현 스펙으로 삼아 재개하면 된다.

## 배경 — origin/feature/outgame과의 충돌 경위

애초에는 "맵 선택→진영", "진영→전투시작", "인게임→맵선택(전투 종료)" 세 전환 지점 모두에
로딩 오버레이 + 의지의 파편 게이트를 걸려고 했다. 그런데 origin/feature/outgame을 pull 받아보니
`d539c4c feat: 인게임 로딩 씬 + 진영 UI 재설계` 커밋이 이미 "진영→전투시작" 지점에 별도의
`Loading.unity` 전용 씬(`LoadingHandoff`/`LoadingScreenController`)을 만들어놨었다 — 배치 확정
직후 씬 전환 사이에 스카이박스가 비치던 실제 버그를 고치면서(패널을 미리 안 닫음), 최소 표시
시간(0.6~0.8초)까지 보장하는 완성도 있는 구현이었다.

**결론**: 이 두 시스템은 같은 지점을 다른 방식으로 처리해 병존시킬 수 없었고, 사용자가 직접
범위를 재조정했다 — "진영→전투시작"은 origin의 Loading.unity에 완전히 맡기고, **의지의 파편은
"인게임→맵선택(전투 종료)" 전환 단 한 곳에서만** 동작하도록 축소.

## 확정된 동작 (사용자 원문 확정, 2026-08-04)

> "의지의 파편은 전투가 끝났을 때만 실행되도록 하자. 전투가 끝나면 의지의 파편 시스템이 일단
> 화면에 검은 오버레이를 띄우고 확률 계산을 해서 확률이 뜨면 이벤트 보여주고 클릭 받고 아니면
> 그냥 클릭 받아서 아웃게임으로 넘기고"

즉:
1. 전투 종료 → 아웃게임(맵 화면) 복귀 전환 시점에만 트리거.
2. 화면에 검은 오버레이를 띄운다.
3. 낮은 확률(기본 15%, [[story-worldbuilding]] 메모의 "의지의 파편은 아주 드묾" 설정과 합의된
   수치 — 매번 뜨면 "드묾"이 깨진다는 지적에 사용자가 직접 정함)로 판정.
4. 확률에 걸리면 "의지의 파편" 텍스트를 보여주고 클릭을 받는다.
5. 확률에 안 걸려도 **똑같이 클릭을 받아야** 다음(맵 화면)으로 넘어간다 — 파편 유무와 무관하게
   항상 한 번의 클릭이 필요하다는 점이 포인트(빈 화면이든 파편이 있든 "탭하여 계속" 형태의 일관된
   비트).

맵 선택→진영, 진영→전투시작 두 지점은 이 시스템이 건드리지 않는다(origin의 Loading.unity가
전자만 담당하고, 맵→진영은 애초에 로딩할 게 없어서 논의에서 제외됨).

## 구현 스펙 (되돌리기 전 실제로 짰던 코드 기준)

### 1. 순수 로직 — `Assets/OutGame/Scripts/Logic/Narrative/`

```csharp
// LoreFragmentData.cs — EventData와 동일한 패턴의 순수 데이터
[Serializable]
public class LoreFragmentData
{
    public string id;
    public string text;
}
```

```csharp
// LoreFragmentSelector.cs — EventSelector와 달리 반복 방지 로직 없음(확률 자체가 낮아 불필요)
public static class LoreFragmentSelector
{
    public const float DefaultTriggerChance = 0.15f;

    public static bool TrySelect(
        IReadOnlyList<LoreFragmentData> pool, Random rng, float triggerChance, out LoreFragmentData selected)
    {
        selected = null;
        if (pool.Count == 0) return false;
        if (rng.NextDouble() >= triggerChance) return false;
        selected = pool[rng.Next(pool.Count)];
        return true;
    }
}
```

### 2. ScriptableObject — `Assets/OutGame/Scripts/ScriptableObjects/LoreFragmentDefinition.cs`

`EventDefinition`과 동일 패턴이지만 선택지/보상 없이 `fragmentId` + `text`(TextArea) 두 필드뿐.
`Resources.LoadAll<LoreFragmentDefinition>("OutGame/Data/LoreFragments")`로 자동 수집(다른
Definition들과 동일한 무등록 방식).

### 3. 문안 12종 (기존 초안 2종 + 신규 10종, 톤 검수 완료)

세계관 문서([[story-worldbuilding]])의 "의지의 파편 = 애틋하고 쓸쓸함, 설명하지 않고 여운만
남김" 톤 규칙을 지켜 작성했던 최종 문안 — 재구현 시 그대로 재사용 가능:

1. **이름 한 조각** — "행군 중이던 흙인형 하나가 문득 걸음을 멈추고 낮게 무언가를 읊조린다. 이름
   같기도 하고, 아닌 것 같기도 하다. 다음 걸음에는, 이미 아무 일도 없었다는 듯 다시 대열로
   돌아간다."
2. **흥얼거림** — "야영 중, 보초를 서던 흙인형 하나가 낮게 콧노래 같은 소리를 흘린다. 곡조랄
   것도 없는 짧은 소절 — 이내 다시, 아무 소리도 내지 않는다."
3. **뒷모습** — "대열 사이, 흙인형 하나가 문득 걸음을 늦춘다. 저만치 앞서 걷는 다른 흙인형의
   뒷모습을 오래 바라보다가 — 이내 다시, 원래의 보폭으로 돌아간다."
4. **들꽃** — "부서진 담장 곁을 지나던 흙인형이 잠시 멈춰 선다. 담장 아래 핀 들꽃 한 송이를

5. **별 보기** — "밤이 깊어도 흙인형들은 잠들지 않는다. 그런데 오늘은 한 흙인형이 유독 오래도록
   하늘을 올려다보고 있다. 별을 세는 것도, 무언가를 기다리는 것도 아니다. 그저, 바라보고 있을
   뿐이다."
6. **허공에 쓰기** — "행군 대열 한쪽에서, 흙인형 하나가 허공에 손가락으로 무언가를 그린다. 글자
   같기도, 그림 같기도 하다. 완성되기 전에 손은 다시 창을 쥔다."
7. **아이 웃음소리** — "멀리서 아이 웃음소리가 들려온 순간, 앞서 걷던 흙인형의 어깨가 미세하게
   움찔거렸다. 뒤돌아보지는 않는다. 그저 걸음이 아주 잠깐, 무거워졌을 뿐이다."
8. **빈 손바닥** — "휴식 중이던 흙인형 하나가, 제 손바닥을 오래도록 들여다본다. 굳은살도, 상처도

### 4. UI 컴포넌트 — `Assets/OutGame/Scripts/UI/LoadingOverlayPanel.cs`

**중요한 설계 결정**: 처음엔 세 지점을 다 덮으려고 `DontDestroyOnLoad` 싱글톤(`GetOrCreate()`)으로
만들었으나, 범위가 "전투 종료→맵" 한 지점으로 좁혀지면서 **싱글톤/DontDestroyOnLoad가 필요 없어짐**
— `OutGameFlowController`가 소유하는 일반 인스턴스로 충분하다(OutGame.unity 생애주기 안에서만
쓰이고 씬과 함께 자연히 파괴됨). 재구현 시 처음부터 이 단순한 형태로 만들 것 — 싱글톤으로 갔다가
되돌리는 시행착오를 반복할 필요 없음.

```csharp
public class LoadingOverlayPanel : MonoBehaviour
{
    [SerializeField] private GameObject spinnerRoot;   // 미사용 상태로 둬도 무방(항상 fragmentRoot만 사용)
    [SerializeField] private GameObject fragmentRoot;
    [SerializeField] private Text fragmentText;
    [SerializeField] private Button continueButton;

    public float FragmentTriggerChance = LoreFragmentSelector.DefaultTriggerChance; // 테스트에서 0/1로 고정 가능

    private System.Random rng;
    private LoreFragmentData[] fragmentPool;
    private bool continueClicked;

    private void Awake()
    {
        // null 체크 fail-fast, rng 초기화, Resources.LoadAll로 fragmentPool 채우기,
        // continueButton.onClick.AddListener(() => continueClicked = true), gameObject.SetActive(false)
    }

    public void Begin(Action onComplete)
    {
        gameObject.SetActive(true);
        StartCoroutine(RunCoroutine(onComplete));
    }

    private IEnumerator RunCoroutine(Action onComplete)
    {
        LoreFragmentSelector.TrySelect(fragmentPool, rng, FragmentTriggerChance, out var fragment);
        fragmentRoot.SetActive(true);
        fragmentText.gameObject.SetActive(fragment != null); // 파편 없으면 빈 화면 + 버튼만
        if (fragment != null) fragmentText.text = fragment.text;

        continueClicked = false;
        yield return new WaitUntil(() => continueClicked); // 항상 클릭 대기 — 파편 유무 무관

        gameObject.SetActive(false);
        onComplete?.Invoke();
    }
}
```

### 5. 프리팹 — `Resources/OutGame/LoadingOverlay.prefab`

다른 UI 패널(`DummyRoomPanel.prefab` 등)과 달리 **루트 자체가 완전한 Canvas**여야 한다는 점은
더 이상 유효하지 않다 — 싱글톤을 버렸으므로 OutGame.unity 기존 Canvas의 자식으로 두는 일반적인
방식(다른 패널들과 동일)으로 만들면 된다. 계층 구조 제안:

```
LoadingOverlay (RectTransform, LoadingOverlayPanel, 기본 비활성)
├─ Background (Image, 풀스크린, 짙은 배경)
└─ FragmentRoot (RectTransform 컨테이너)
    ├─ FragmentText (Text, 중앙 정렬, 멀티라인)
    └─ ContinueButton (Button, "계속하기")
```

씬(OutGame.unity)에 직접 배치하고 `OutGameFlowController`의 필드로 배선(다른 패널들과 동일한
`[SerializeField]` + Awake() null 체크 fail-fast 패턴). 배선 누락 시 `Resources.Load` 폴백도
가능(다른 컨트롤러들의 관례).

### 6. 배선 지점 — `OutGameFlowController.cs`

```csharp
[SerializeField] private LoadingOverlayPanel loadingOverlay;

private void Start()
{
    RunState pendingRun = RunSessionContext.ConsumePendingRun();
    if (pendingRun != null)
    {
        loadingOverlay.Begin(() =>
        {
            ShowOnly(roomGraphController.gameObject);
            roomGraphController.Begin(pendingRun);
        });
    }
    else
    {
        ShowOnly(mapSelectPanel.gameObject);
    }
}
```

`InGameFlowController.cs`는 건드릴 필요 없음 — "진영→전투시작"은 origin의 `LoadingHandoff`/
`Loading.unity`가 이미 전담.

### 7. 테스트 결정성 주의점 (재구현 시 처음부터 반영)

- `LoadingOverlayPanel.FragmentTriggerChance`를 테스트에서 0으로 고정하거나, 오버레이가 뜬 걸
  감지해 `ContinueButton`을 항상 클릭해 넘기는 헬퍼를 만들 것(확률과 무관하게 결정적으로 통과).
- 싱글톤이 아니므로 `DontDestroyOnLoad` 관련 `ResetForTests()` 같은 정적 정리 코드는 불필요.

## 남은 작업 (Unity 에디터 접근 가능한 환경에서)

1. 위 스크립트 4개(`LoreFragmentData`, `LoreFragmentSelector`, `LoreFragmentDefinition`,
   `LoadingOverlayPanel`) 재작성.
2. `Resources/OutGame/Data/LoreFragments/`에 위 12종 텍스트로 `LoreFragmentDefinition` 에셋 생성.
3. `LoadingOverlay` 프리팹을 OutGame.unity 기존 Canvas 자식으로 제작, `OutGameFlowController`에
   배선.
4. `OutGameFlowController.Start()`의 `pendingRun` 분기 수정.
5. `ResourcePaths.cs`에 `LoreFragments`/`LoadingOverlay` 경로 상수 추가.
6. EditMode(`LoreFragmentSelector` 순수 로직 테스트) + PlayMode(`OutGameFlowControllerPlayTests`
   등) 테스트를 **실제로 Unity Test Runner에서 실행**해 확인 — 이 문서를 만든 세션에서는 그 실행
   자체가 불가능했다는 점이 되돌린 이유였다.
