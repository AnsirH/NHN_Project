### 크로스 런타임 결정론 조사 기록 (증상 → 소거 실험 → 원인 판단 → 계약 재정의)

1. **증상**: 교차 검증(승자/종료 틱 완전 일치 요구)에서 불일치 발견 —
   방진 시나리오(삼각함수 미사용) 시드 0·1·2 비트 단위 일치 후 시드 3에서 2틱 차,
   일제 사격 시나리오 시드 1에서 1틱 차. 관찰된 모든 판에서 승자는 일치.
2. **소거 실험**: 사전 예상 원인은 MathF.Sin/Cos(초월함수)와 SIMD였으나 —
   ① 삼각함수 없는 시나리오에서도 발생 → 초월함수 단독 원인 배제.
   ② `DOTNET_EnableFMA=0` 재실행 → 변화 없음 → FMA 배제.
   ③ `DOTNET_EnableHWIntrinsic=0` 재실행(실행 3배 느려짐 = 플래그 적용 확인) → 변화 없음 → 인트린식 전체 배제.
3. **원인 판단**: 수백 틱 동안 비트 단위로 일치하다 드문 판에서만 1~2틱 갈라지는 패턴 —
   Mono JIT가 float 중간값을 확장 정밀도로 유지(ECMA CIL이 허용)하는 것과 CoreCLR의 연산별
   엄격 반올림의 차이로 판단. 반올림 경계에 걸린 드문 비교 하나가 뒤집히는 전형.
   C# 코드 수정으로 신뢰성 있게 제거 불가(두 JIT의 허용된 동작 차이).
4. **계약 재정의 (승인)**: 비트 결정론 요구를 폐기하고 **정본 분리** —
   밸런싱 통계 정본 = CLI, 리플레이 정본 = 에디터 자체 시뮬. 교차 검증은 두 정본의
   통계적 등가성 감시 장치로 재정의: **승자 불일치 무관용 FAIL + 시드 100개**
   ("100시드 승자 뒤집힘 0건"이 신뢰 근거). 작업 4 리플레이 완료 기준도 동일 계약 적용.
4-1. **틱 허용치 재조정 (실측 기반)**: 1차 승인안 ±5틱(절대)으로 100시드를 돌리자 두 시나리오 모두
   4분의 1 시드에서 초과 — 승자 뒤집힘은 0/200건. 분포를 보니 드리프트는 고정 오차가 아니라
   **나비효과**였다: 반올림 경계에서 갈라진 뒤 종료 시점 차이가 전투 길이·혼전도에 비례해 커진다
   (방진 최대 18틱=5.1%, 광역 산포가 있는 일제 사격 최대 50틱=15.3%). 절대 틱 기준은 시나리오
   길이가 바뀔 때마다 무의미해지므로 **상대 오차 ±20%**로 재정의해 승인·반영. 결과 EditMode 20/20 통과.
   교훈: 허용 오차는 오차의 "생성 메커니즘"에 맞춰 정의해야 한다 — 나비효과는 상대 기준이어야 한다.
5. **잼 이후 과제**: 완전한 크로스 런타임 결정론이 필요해지면 시뮬 수학을 고정소수점으로 전환
   (옵션 C — Simulation 전면 수정·성능 하락·기존 밸런스 미세 변동을 수반하므로 잼 스코프 제외).

## 2026-07-24 — 5.6-A단계: 전투 스탯 확장 (방어력 감쇠 + 치명타)

- **배경**: 아웃게임 팀과 스탯 5종(체력/공격력/방어력/치명타확률/이동속도) 합의. 방어력·치명타가
  시뮬에 없어 추가. 스탯 계산 주체는 아웃게임(전달받는 구조)이지만, 시뮬은 그 값들을 실행할 수 있어야 한다.
- **합의 규칙 반영**: 방어력 = 감쇠 공식 `피해 × K/(K+방어력)` (K는 BattleConfig 데이터),
  치명타 확률 = 퍼센트 정수(0~100, 아웃게임 표기 단위와 동일), 치명타 배율 = 1.8 전역.
  방어력은 일반 공격·투사체·장군 액티브·플레이어 스킬 즉발에 적용, **도트(중독/화상)에는 미적용**
  (상태이상 셋업의 가치 보존) → 피해 누적기를 `_pendingDamage`(감쇠 대상)와
  `_pendingDotDamage`(감쇠 제외)로 분리.
- **회귀 방어 설계**: 치명타 확률이 0이면 난수를 **뽑지 않는다**. 기존 에셋은 방어력·치명타가 전부 0이라
  감쇠 배율 1 + 난수 소비 0 → 기존 전투 결과가 비트 단위로 보존된다.
  실측 확인: BalanceLab 시드 0 전투가 확장 전후 모두 339틱으로 동일, 500판 승률도 동일.
- **확정 치명타(그림자 습격)와의 관계**: 무장된 확정 치명타가 있으면 확률 추첨을 건너뛰고 그것을 소비한다
  — 이중 적용 방지 + 장군 액티브의 정체성 보존.
- **검증**: 신규 테스트 4종(감쇠 공식 수치, 도트 미적용, 치명타 배율/0% 기본값, 회귀 보존) →
  EditMode 24/24 통과. CLI(.asset 직독)도 새 필드 파싱 반영.

## 2026-07-24 — 5.6-B단계: 스탯 결합 팩토리 (아웃게임 전달 스탯 ↔ 인게임 속성)

- **설계 문제**: 스탯 계산 주체가 아웃게임이 되면서 한 유닛의 정의가 두 출처로 쪼개졌다 —
  5스탯(아웃게임 전달)과 인게임 속성(.asset: 공격 주기·사거리·투사체·타겟팅·이동 패턴·반경).
  RoleDefinition은 불변(readonly)이라 값을 꽂아 넣을 수 없다.
- **해결**: 결합 팩토리 `RoleDefinition.WithStats(baseRole, 5스탯)` — 인게임 속성은 승계하고
  5스탯만 교체한 새 인스턴스를 만든다. 장군은 `GeneralDefinition.WithCombatRole`로 능력(패시브·충전·
  액티브)은 유지한 채 전투 능력만 교체. 불변을 지켜 시뮬 결정론이 깨지지 않고, 분대별 인스턴스라
  **같은 장군 에셋이 레벨이 다른 여러 분대에 동시에 쓰여도 간섭이 없다**(회의 확정 모델).
  .asset을 런타임에 수정하지 않아 에디터 에셋 오염 사고도 원천 차단된다.
- **경로 통합**: `SquadRequest.maxHp > 0`이면 전달값, 아니면 .asset 값 — 연결 경로와 로컬 경로
  (테스트 씬·BalanceLab)가 같은 빌더 코드를 탄다. 시뮬 본체는 어느 쪽인지 알 필요가 없다.
- **회의 확정 모델 반영**: 모든 분대에 장군 1명(빈 슬롯은 분대 없음), 병과는 아이템이 부여하고
  그 병과가 장군 스킬을 결정 → GeneralData 4종 + 노멀 1종으로 충분. 레벨 축은 하나(0~5, 장군 레벨).
- **검증**: 신규 테스트 3종(전달 스탯 적용 + 인게임 속성 보존, 미전달 시 .asset 폴백,
  같은 에셋 다른 레벨 분대 간 비간섭) → EditMode 27/27 통과. BalanceLab 회귀도 유지(시드0 339틱).

## 2026-07-24 — 5.6-C1단계: 스탯 CSV 파이프라인 (두 팀 공유 계약서)

- **문제**: 스탯 계산 주체가 아웃게임이 되면서, BalanceLab이 .asset을 아무리 튜닝해도 실제 게임이
  쓰는 5스탯에는 반영되지 않는 구조가 됐다 — 밸런싱이 헛돌 수 있는 위험.
- **해결 구조**: 구글 시트(원본) → CSV(커밋) → ①아웃게임이 계산에 사용 ②인게임 .asset에 임포트.
  AI 튜닝은 .asset을 고치므로 **역방향 익스포터**로 CSV에 되돌려 시트에 반영 → 두 팀 수치가 하나로 유지.
- **전개 테이블 채택**(배율 테이블 아님): 병과 × 레벨(0~5) 값을 그대로 적는다. 양 팀이 각자 계산식을
  구현하면 반올림·적용 순서 차이로 수치가 조용히 어긋나는데, 값을 적으면 어긋날 여지 자체가 없다.
