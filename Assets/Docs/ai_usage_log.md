### 크로스 런타임 결정론 조사 기록 (증상 → 소거 실험 → 원인 판단 → 계약 재정의)

1. **증상**: 교차 검증(승자/종료 틱 완전 일치 요구)에서 불일치 발견 —
   방진 시나리오(삼각함수 미사용) 시드 0·1·2 비트 단위 일치 후 시드 3에서 2틱 차,
   일제 사격 시나리오 시드 1에서 1틱 차. 관찰된 모든 판에서 승자는 일치.
2. **소거 실험**: 사전 예상 원인은 MathF.Sin/Cos(초월함수)와 SIMD였으나 —
   ① 삼각함수 없는 시나리오에서도 발생 → 초월함수 단독 원인 배제.
   ② `DOTNET_EnableFMA=0` 재실행 → 변화 없음 → FMA 배제.
   ③ `DOTNET_EnableHWIntrinsic=0` 재실행(실행 3배 느려짐 = 플래그 적용 확인) → 변화 없음 → 인트린식 전체 배제.
3. **원인 판단**: 수백 틱 동안 비트 단위로 일치하다 드문 판에서만 1~2틱 갈라지는 패턴 —
   Mono JIT가 float 중간값을 확장 정밀도로 유지(ECMA CIL이 허용)하는 것과 CoreCLR의 연산별
   엄격 반올림의 차이로 판단. 반올림 경계에 걸린 드문 비교 하나가 뒤집히는 전형.
   C# 코드 수정으로 신뢰성 있게 제거 불가(두 JIT의 허용된 동작 차이).
4. **계약 재정의 (승인)**: 비트 결정론 요구를 폐기하고 **정본 분리** —
   밸런싱 통계 정본 = CLI, 리플레이 정본 = 에디터 자체 시뮬. 교차 검증은 두 정본의
   통계적 등가성 감시 장치로 재정의: **승자 불일치 무관용 FAIL + 시드 100개**
   ("100시드 승자 뒤집힘 0건"이 신뢰 근거). 작업 4 리플레이 완료 기준도 동일 계약 적용.
4-1. **틱 허용치 재조정 (실측 기반)**: 1차 승인안 ±5틱(절대)으로 100시드를 돌리자 두 시나리오 모두
   4분의 1 시드에서 초과 — 승자 뒤집힘은 0/200건. 분포를 보니 드리프트는 고정 오차가 아니라
   **나비효과**였다: 반올림 경계에서 갈라진 뒤 종료 시점 차이가 전투 길이·혼전도에 비례해 커진다
   (방진 최대 18틱=5.1%, 광역 산포가 있는 일제 사격 최대 50틱=15.3%). 절대 틱 기준은 시나리오
   길이가 바뀔 때마다 무의미해지므로 **상대 오차 ±20%**로 재정의해 승인·반영. 결과 EditMode 20/20 통과.
   교훈: 허용 오차는 오차의 "생성 메커니즘"에 맞춰 정의해야 한다 — 나비효과는 상대 기준이어야 한다.
5. **잼 이후 과제**: 완전한 크로스 런타임 결정론이 필요해지면 시뮬 수학을 고정소수점으로 전환
   (옵션 C — Simulation 전면 수정·성능 하락·기존 밸런스 미세 변동을 수반하므로 잼 스코프 제외).

## 2026-07-24 — 5.6-A단계: 전투 스탯 확장 (방어력 감쇠 + 치명타)

- **배경**: 아웃게임 팀과 스탯 5종(체력/공격력/방어력/치명타확률/이동속도) 합의. 방어력·치명타가
  시뮬에 없어 추가. 스탯 계산 주체는 아웃게임(전달받는 구조)이지만, 시뮬은 그 값들을 실행할 수 있어야 한다.
- **합의 규칙 반영**: 방어력 = 감쇠 공식 `피해 × K/(K+방어력)` (K는 BattleConfig 데이터),
  치명타 확률 = 퍼센트 정수(0~100, 아웃게임 표기 단위와 동일), 치명타 배율 = 1.8 전역.
  방어력은 일반 공격·투사체·장군 액티브·플레이어 스킬 즉발에 적용, **도트(중독/화상)에는 미적용**
  (상태이상 셋업의 가치 보존) → 피해 누적기를 `_pendingDamage`(감쇠 대상)와
  `_pendingDotDamage`(감쇠 제외)로 분리.
- **회귀 방어 설계**: 치명타 확률이 0이면 난수를 **뽑지 않는다**. 기존 에셋은 방어력·치명타가 전부 0이라
  감쇠 배율 1 + 난수 소비 0 → 기존 전투 결과가 비트 단위로 보존된다.
  실측 확인: BalanceLab 시드 0 전투가 확장 전후 모두 339틱으로 동일, 500판 승률도 동일.
- **확정 치명타(그림자 습격)와의 관계**: 무장된 확정 치명타가 있으면 확률 추첨을 건너뛰고 그것을 소비한다
  — 이중 적용 방지 + 장군 액티브의 정체성 보존.
- **검증**: 신규 테스트 4종(감쇠 공식 수치, 도트 미적용, 치명타 배율/0% 기본값, 회귀 보존) →
  EditMode 24/24 통과. CLI(.asset 직독)도 새 필드 파싱 반영.

## 2026-07-24 — 5.6-B단계: 스탯 결합 팩토리 (아웃게임 전달 스탯 ↔ 인게임 속성)

- **설계 문제**: 스탯 계산 주체가 아웃게임이 되면서 한 유닛의 정의가 두 출처로 쪼개졌다 —
  5스탯(아웃게임 전달)과 인게임 속성(.asset: 공격 주기·사거리·투사체·타겟팅·이동 패턴·반경).
  RoleDefinition은 불변(readonly)이라 값을 꽂아 넣을 수 없다.
- **해결**: 결합 팩토리 `RoleDefinition.WithStats(baseRole, 5스탯)` — 인게임 속성은 승계하고
  5스탯만 교체한 새 인스턴스를 만든다. 장군은 `GeneralDefinition.WithCombatRole`로 능력(패시브·충전·
  액티브)은 유지한 채 전투 능력만 교체. 불변을 지켜 시뮬 결정론이 깨지지 않고, 분대별 인스턴스라
  **같은 장군 에셋이 레벨이 다른 여러 분대에 동시에 쓰여도 간섭이 없다**(회의 확정 모델).
  .asset을 런타임에 수정하지 않아 에디터 에셋 오염 사고도 원천 차단된다.
- **경로 통합**: `SquadRequest.maxHp > 0`이면 전달값, 아니면 .asset 값 — 연결 경로와 로컬 경로
  (테스트 씬·BalanceLab)가 같은 빌더 코드를 탄다. 시뮬 본체는 어느 쪽인지 알 필요가 없다.
- **회의 확정 모델 반영**: 모든 분대에 장군 1명(빈 슬롯은 분대 없음), 병과는 아이템이 부여하고
  그 병과가 장군 스킬을 결정 → GeneralData 4종 + 노멀 1종으로 충분. 레벨 축은 하나(0~5, 장군 레벨).
- **검증**: 신규 테스트 3종(전달 스탯 적용 + 인게임 속성 보존, 미전달 시 .asset 폴백,
  같은 에셋 다른 레벨 분대 간 비간섭) → EditMode 27/27 통과. BalanceLab 회귀도 유지(시드0 339틱).

## 2026-07-24 — 5.6-C1단계: 스탯 CSV 파이프라인 (두 팀 공유 계약서)

- **문제**: 스탯 계산 주체가 아웃게임이 되면서, BalanceLab이 .asset을 아무리 튜닝해도 실제 게임이
  쓰는 5스탯에는 반영되지 않는 구조가 됐다 — 밸런싱이 헛돌 수 있는 위험.
- **해결 구조**: 구글 시트(원본) → CSV(커밋) → ①아웃게임이 계산에 사용 ②인게임 .asset에 임포트.
  AI 튜닝은 .asset을 고치므로 **역방향 익스포터**로 CSV에 되돌려 시트에 반영 → 두 팀 수치가 하나로 유지.
- **전개 테이블 채택**(배율 테이블 아님): 병과 × 레벨(0~5) 값을 그대로 적는다. 양 팀이 각자 계산식을
  구현하면 반올림·적용 순서 차이로 수치가 조용히 어긋나는데, 값을 적으면 어긋날 여지 자체가 없다.
  5병과 × 6레벨 = 30행이라 관리 부담도 작다.
- **파서 단일화**: StatTable을 Simulation(순수 C#, 파일 I/O 없음)에 두어 **에디터 임포터와 CLI가
  같은 파서 하나**를 공유한다 — 파서가 둘이면 해석이 갈라진다. 헤더·열 수·수치·중복·레벨 누락 전부 fail-fast.
- **불일치 가드**: CLI가 실행 시 CSV 레벨 0 ↔ .asset 스탯을 비교해 다르면 즉시 실패 —
  "임포트 안 하고 튜닝 돌린" 사고 차단. 실측 검증: Warrior maxHp를 100→111로 바꾸자
  `Warrior.maxHp: 에셋 111 vs CSV 100`으로 정확히 잡고 종료 코드 1 반환.
- **노멀 장군 추가**: 아이템 미부여(ArmyClass.None) 분대용 — 패시브/충전/액티브 전부 None,
  스탯만 높고 크기 배율은 유지(즉시 구분). 회의 확정 모델("모든 분대에 장군 1명")의 빈자리를 채운다.
- **부수 효과**: 임포터의 에셋 재저장으로 v4에서 삭제된 옛 병사 기믹 필드 잔재가 정리됐다.
- **검증**: 임포터 10개 에셋 반영 / 익스포터 왕복 무손실(주석·레벨 1~5 행 보존) /
  신규 테스트 5종 → EditMode 32/32 통과, BalanceLab 회귀 유지(시드0 339틱).

## 2026-07-24 — 5.6-C2단계: CLI 레벨 스윕 (실전과 같은 결합 경로로 밸런싱)

- **핵심 설계**: CLI가 `.asset`(인게임 속성) + `CSV`(해당 레벨 5스탯)를 `RoleDefinition.WithStats`로 결합한다 —
  실제 게임의 연결 경로(아웃게임이 스탯을 전달하는 구조)와 **같은 결합 함수**를 타므로 밸런싱이 실전 코드로 검증된다.

  교차 검증 시나리오가 레벨 0이 아니면 테스트가 즉시 실패하게 강제했다. 방치했다면 두 쪽이 서로 다른
  스탯으로 싸우면서 "정본 등가성 검증"이 조용히 무의미해졌을 것이다.
- **에셋 이름 규약 공유**: `<병과>General` 규약을 StatTable(Simulation)로 올려 에디터·CLI가 함께 쓴다.
- **첫 레벨 스윕 실측** (warrior_lv0_vs_lv5, 200판): 레벨 5가 **200/200 승**, 평균 잔존 19.4/20명,
  장군 200판 전부 생존. 레벨 격차가 압도적임을 수치로 확인 — 밸런싱(작업 5)의 입력 데이터.

## 2026-07-24 — BalanceLab 작업 2: 목표 밴드 판정 + 시나리오 매트릭스

- **리드 오프셋 데이터 승격**: 장군 스폰 위치의 코드 상수(-1 랭크)를 GeneralData 필드로 옮기고
  **-1~+1 랭크로 클램프**(승인 조건) — 에디터는 [Range]+OnValidate, CLI는 범위 밖 값이면 즉시 실패.
  CLI가 조용히 보정하지 않는 이유: 튜닝 루프가 "값을 바꿨는데 결과가 그대로"인 혼란에 빠지지 않도록.
- **밴드 판정**: bands.json(general_vs_none 65~75% / mirror_general 45~55% / role_matchup 30~70% / none)
  + 시나리오의 `band` 태그. 좌군 승률로 PASS/FAIL. 미등록 태그는 즉시 실패(오타가 무판정으로 새지 않게).
- **시나리오 세트**: `@상대경로` 군대 참조로 재사용 + `scenarios/all.json` 세트 파일 →
  `dotnet run -- scenarios/all.json` 한 번에 14개 매트릭스 실행. 종료 코드 3 = 밴드 FAIL 존재(튜닝 루프용).
- **파서 보완**: 에디터가 에셋을 재저장하면 enum 리스트가 16진 바이트 문자열("0100000002000000")로
  직렬화된다는 것을 매트릭스 실행 중 발견 — YAML 목록/빈 값/16진 세 형태를 모두 지원하게 보완했다.
  (임포터가 에셋을 건드리자 드러난 문제 — fail-fast 파서가 조용한 오해석 대신 즉시 알려준 사례)
- **첫 전체 매트릭스 실측 (각 200판, 14개)**: **1 PASS / 13 FAIL**. 도구가 제 역할을 하는 상태이며
  수치 튜닝은 작업 5의 몫. 다만 **미러 매치업 실패는 성격이 다르다** — 동일 구성인데
  암살자 16.5%, 사냥꾼 40.0%, 전사 57.5%로 좌/우 편향이 나타났다(궁수만 52% PASS).
  데이터가 아니라 시뮬 구조(유닛 인덱스 순서에 얽힌 처리 순서·재탐색 시차 등)의 문제로 보이며,
  이대로 튜닝에 들어가면 모든 밸런스 수치가 오염되므로 **작업 5 이전에 원인 규명이 필요**하다고 보고했다.
- **검증**: 리드 오프셋 데이터화·클램프 테스트 추가 → EditMode 33/33 통과.

## 2026-07-26 — 5.7단계: 아웃게임 계약 확정본 추종 (CSV 폐기 + 스탯 재구성 모델)

- **배경**: dev 브랜치(= feature/outgame)를 확인하니 우리 요청서가 상당 부분 반영돼 있었다 —
  `ArmyClass`가 4병과(Warrior/Archer/Hunter/Assassin)로 확장되고 `Shieldman`이 `Warrior`로 개칭돼
  **양 팀 어휘가 일치**했고, 씬 전환 핸드오프(`SetPendingBattle`/`ConsumePendingSetup`/`CompleteBattle`)도 추가됐다.
- **다만 스탯 전달은 반대 방향으로 결정됐다** (§7.1.1): 스탯을 계약에 넣지 않고
  `armyDefId` + `upgradeLevel`만 넘긴 뒤 **인게임이 `ArmyStatCalculator`로 재구성**하는 모델.
  근거가 타당했다 — "각자 계산하면 어긋난다"를 두 번 버그로 겪었고(전투력 계산이 업그레이드를 놓친 사례),
  그래서 헬퍼 단일화가 규칙이 됐다. 확인해보니 그 헬퍼는 UnityEngine 참조가 없는 순수 C#이라
  BalanceLab에도 링크 컴파일로 재사용할 수 있다 → 우리 도구까지 같은 계산을 공유할 수 있어 정합성이 더 높다.
- **판단**: 아웃게임 모델을 그대로 따르고, 인게임 CSV 파이프라인을 **폐기**했다.
  플레이어 부대 스탯 정본이 아웃게임 `ArmyDefinition`으로 확정된 순간, 우리 CSV는 중복 출처가 되어
  "튜닝했는데 게임엔 반영 안 되는" 함정이 되기 때문이다. 하루 전 만든 파이프라인을 스스로 걷어낸 셈이지만,
  출처가 둘인 상태를 유지하는 비용이 훨씬 크다.
- **레벨 스윕도 함께 제거**: 배율 공식(+10%/레벨)을 툴에서 임시로 재현하면 그쪽이 경고한 바로 그
  "공식 이중화"를 만든다. 머지 후 `ArmyStatCalculator`를 링크해 되살리는 쪽이 옳다.
- **수신 모델 재구성**: 병사 3스탯(체력·공격력·방어력) + 장군 3스탯 + **공유 2스탯**(치명타·이동속도 —
  아웃게임 §5.7대로 유닛이 장군 값을 그대로 쓴다). 필드 10개 → 8개로 줄었다.
- **커넥터 재작성**: `armyDefId` → `ArmyData` 원형 조회 → `ArmyStatCalculator` 배율 곱 → `SquadRequest`.
  씬 핸드오프 수신, 이동속도 단위 환산(100 → 3.5), 병과 4종 1:1 매핑, 장군은 병과에서 파생.
