# BalanceLab 밸런스 뷰어 — 설계 문서

> 작성일: 2026-08-10
> 대상: `Tools/BalanceLab` CLI의 결과를 사람이 눈으로 읽고, 수치를 조절하고, 전투를 재생해 보는 정적 웹 뷰어.
> 원칙: 이 문서에 없는 기능은 만들지 않는다.

---

## 1. 목적과 배경

현재 밸런싱 파이프라인은 `Tools/BalanceLab` CLI 하나로 완결돼 있다. 시나리오 JSON을 넣으면 시드 0..N-1로
N판을 돌려 `results/<시나리오>.json`을 쓰고, `bands.json`의 목표 구간과 대조해 PASS/FAIL을 출력한다.
측정 도구로서는 충분하지만 **사람이 밸런스를 잡는 도구로는 두 군데가 막혀 있다.**

1. **결과를 읽기 어렵다.** 14개 시나리오의 PASS/FAIL이 콘솔 텍스트로 흘러가고, 판정의 근거인
   분포·시드별 편차는 JSON을 직접 열어야 보인다.
2. **수치를 바꾸려면 Unity를 켜야 한다.** 스탯 정본이 `Assets/Data/*.asset`이라 값 하나를 실험하려 해도
   에디터 기동 → 인스펙터 수정 → 저장 → CLI 재실행이라는 왕복이 필요하다. 이게 튜닝 루프의 실질적 병목이다.
3. **전투를 볼 수 없다.** 승률이 왜 그렇게 나왔는지 — 진형이 무너졌는지, 장군이 먼저 죽었는지,
   원거리가 사거리 밖에서 놀았는지 — 를 수치만으로는 알 수 없다.

이 문서는 그 셋을 푸는 **정적 웹 뷰어**와 그것이 요구하는 **CLI 확장**을 설계한다.

부수 효과로 이 도구는 잼 제출물 중 「AI 활용 기술 문서」의 증거물이 된다. 게임 빌드(APK)와 완전히 분리된
정적 페이지라 제출 빌드 제약과 충돌하지 않으며, GitHub Pages에 올리면 링크 하나로 밸런싱 루프 전체를
보여줄 수 있다.

## 2. 선행 결정 — 리플레이 정본을 CLI로 옮긴다

`Tools/BalanceLab/README.md`의 「정본 분리 원칙」은 원래 이렇게 정해져 있었다.

| 역할 | 기존 정본 |
|---|---|
| 밸런싱 통계 (승률·분포) | CLI (.NET) |
| 시드 리플레이 (눈 검증) | 에디터 자체 시뮬 (Mono) |

**이 설계는 리플레이 정본을 CLI로 옮긴다.**

이유: 대시보드에서 "좌군 승률 68%, 진 32판 중 시드 17을 보자"를 눌렀을 때 보여줄 판은 **그 승률을 만든
바로 그 판**이어야 한다. 에디터가 같은 시드를 재시뮬하면 크로스 런타임 부동소수 드리프트 때문에 다른
전투가 나올 수 있고(README 실측: 최대 상대 드리프트 15.3%), 통계와 화면이 어긋나는 순간 밸런싱 도구로서의
의미가 사라진다.

변경 후 역할 분담:

| 역할 | 정본 |
|---|---|
| 밸런싱 통계 (승률·분포) | **CLI (.NET)** |
| 시드 리플레이 (눈 검증) | **CLI (.NET)** — 통계와 같은 실행에서 나온 궤적 |
| 손맛·연출 확인 | 에디터 테스트 씬 (`BattleTestBootstrap`) — 정본 아님 |

`BalanceLabCrossCheckTests`는 폐기하지 않는다. 오히려 역할이 명확해진다 — *"게임에 실제로 들어가는 Mono
런타임이 CLI 정본과 여전히 통계적으로 같은가"* 를 감시하는 회귀 가드다. 기존 계약(승자 불일치 무관용 FAIL,
종료 틱 상대 ±20%, 시드 100개)은 그대로 유지한다.

이 변경은 `README.md`의 정본 표에도 반영한다.

## 3. 아키텍처

```
[정본 수치]  Assets/Data/*.asset  (SquadData, BattleConfigSO)
                    │  UnityAssetParser → ParsedAsset (필드 사전)
                    ▼
             ┌──────────────┐  ◀── overrides.json  (뷰어가 내보낸 실험 수치)
             │  BalanceLab  │
             │     CLI      │  시드 0..N-1 실행
             └──────┬───────┘
                    ├── results/<시나리오>[.<태그>].json        기존 · 그대로
                    ├── results/<시나리오>[.<태그>].js          신규 · 상세 화면용 래퍼
                    ├── results/index.json + index.js           신규 · 전 시나리오 집계
                    ├── results/assets.js                       신규 · 튜닝 슬라이더 기준선
                    └── results/replay/<시나리오>[.<태그>].<시드>.js   신규 · 궤적
                    ▼
             [정적 웹 뷰어]  Tools/BalanceLab/viewer/index.html
                    │
                    └── 슬라이더 조절 → overrides.json 내보내기 ──┐
                                                                └─▶ 위로 되돌아감
```

### 3.1 불변 원칙

**시뮬레이션 코드(`Assets/Scripts/Simulation/`)는 한 줄도 바꾸지 않는다.**

- 리플레이 레코더는 시뮬 **바깥**에서 매 틱 읽기만 한다. `BattleSimulation`이 이미
  `IsAlive` / `GetPosition` / `GetHp` / `GetTeam` / `IsLeader` / `ViewEvent`를 공개하고 있어 추가 훅이 필요 없다.
- 오버라이드도 시뮬이 아니라 `ParsedAsset` 단계에서 먹인다. `RoleDefinition`은 불변(readonly)이라는
  기존 성질이 유지된다.

이 원칙이 지켜지는 한, 뷰어 기능이 게임 동작을 바꿀 경로가 구조적으로 존재하지 않는다.

## 4. CLI 확장

### 4.1 `--overrides <파일>` — 수치 실험

주입 지점은 **`AssetRepository` 한 곳**이다. 생성자가 `.asset`을 파싱해 만든 `ParsedAsset`(필드 사전)에
패치를 얹는다. `BuildRole`, `LoadBattleConfig`, `GetGeneral`이 전부 그 사전에서 읽으므로, 한 지점만 뚫으면
5스탯 · 공격 주기 · 사거리 · 투사체 · 장군 배율 · 충전 조건 · `BattleConfig`까지 전부 커버된다.

```jsonc
{
  "note": "궁수 사거리 실험 3안",
  "squads": {
    "Archer":         { "attackRange": 14.0, "attackInterval": 1.3 },
    "WarriorGeneral": { "generalHpMultiplier": 2.5 }
  },
  "config": { "defenseK": 120 }
}
```

- `squads` 키는 `SquadData` 에셋 이름. 장군 필드는 `<롤>General` 키로 지정하며, CLI가 기존
  `GeneralSuffix` 규칙대로 접미사를 벗겨 같은 에셋에 적용한다.
- 값 타입은 원본 필드 타입을 따른다. enum 필드는 정수로 준다(`.asset` 표기와 동일).

**규칙 세 가지 (전부 계약):**

1. **미등록 키는 즉시 실패한다.** 존재하지 않는 에셋 이름이나 필드명은 예외. 오타 친 필드가 조용히 무시돼
   "값을 바꿨는데 결과가 그대로"가 되는 것이 튜닝 루프 최악의 함정이다. `AssetRepository`의 기존 fail-fast
   철학(`RequireLeadRankOffsetInRange`의 주석 참조)과 동일하다.
2. **결과 JSON에 오버라이드 원문을 통째로 기록한다.** `ScenarioResult`에 `appliedOverrides` 필드를 추가한다.
   결과 파일만 보고 "이게 무슨 수치로 돈 판인지"를 항상 복원할 수 있어야 한다.
3. **오버라이드가 걸리면 `--tag`가 강제된다.** 태그 없이 `--overrides`를 주면 사용법 오류(종료 코드 2)로
   거절한다. 실험값이 정본 스냅샷(`<시나리오>.json`)을 덮어쓰는 사고를 구조적으로 막는다.

**정본 승격 절차**: 실험 확정 → Unity에서 `.asset`에 손으로 반영 → 태그 없이 재실행 → 정본 갱신.
뷰어는 `.asset`을 쓰지 않는다. 정본은 하나여야 하고, 승격에 사람의 손이 한 번 들어가는 것이 안전장치다.

### 4.2 `--replay <시드>[,<시드>...]` — 궤적 덤프

지정한 시드에 한해 궤적을 기록한다. 200판 전체 덤프 같은 것은 없다(§4.3 용량 참조).

**포맷** — `results/replay/<시나리오>[.<태그>].<시드>.js`

```js
window.BALANCE_REPLAY = window.BALANCE_REPLAY || {};
// 키 = "<시나리오>:<태그 또는 빈문자>:<시드>" — 정본과 태그 실행의 같은 시드가 섞이면 안 된다
window.BALANCE_REPLAY["mirror_warrior::17"] = {
  scenario: "mirror_warrior", seed: 17, tag: null,
  ticks: 387, winner: "right",
  tickRate: 30, sampleEvery: 3,
  arena: { halfWidth: 30, halfHeight: 20 },
  units: [ { team: 0, squad: 0, role: "Warrior", leader: false }, ... ],
  frames: "base64...",
  events: [ { tick: 132, type: "generalActive", unit: 41 }, ... ]
};
```

- **10Hz 샘플링**: 30 tps에서 3틱마다 1프레임. 브라우저가 프레임 사이를 보간해 재생한다.
- **좌표 int16 양자화**: 아레나 ±30 / ±20을 1/100 단위로 담는다. 오차 1cm — 눈으로 구분 불가.
- **프레임당 저장 = 생존 유닛만**: `[유닛인덱스(u16), x(i16), y(i16), hp0~255(u8)]`.
  프레임 헤더에 생존 수를 둔다.
- **`frames`는 전체 프레임 블록을 base64로 묶은 단일 문자열.** 숫자 JSON 대비 3~4배 작다.
- **이벤트는 별도 목록**: 사망 · 장군 액티브 발동 · 플레이어 스킬 · 분대 전멸. 정확한 틱을 보존해야 하는
  정보라 샘플링에 먹히면 안 된다.
- `units`는 전투 시작 시점의 유닛 메타(팀 · 분대 · 롤 · 장군 여부). 전투 중 불변이므로 프레임에서 뺀다.

**예상 크기**: 100유닛 · 12초(≈350틱) 판 기준 60~80KB.

### 4.3 용량 가드

`BattleConfig`의 최악값(`maxUnits: 600`, `maxBattleSeconds: 180`)에서는 단순 덤프가 수 MB가 된다.
샘플링·양자화·생존자만 저장으로 대부분 줄어들지만, 그래도 큰 판은 커진다.

- **덤프 시 예상 크기를 먼저 계산해 콘솔에 출력한다.**
- **2MB를 넘으면 경고를 출력하되 진행한다.** 거절하지 않는 이유: 대규모 난전이야말로 봐야 할 판이다.
  다만 모르고 뜨는 일이 없게 한다.

### 4.4 `results/index.js` — 뷰어 진입점

전 시나리오 집계. 뷰어가 처음 읽는 파일이다.

```js
window.BALANCE_INDEX = {
  generatedAt: "2026-08-10T14:22:11Z",
  scenarios: [
    { name: "mirror_warrior", band: "mirror_general", bandMin: 0.45, bandMax: 0.55,
      runs: 200, leftWinRate: 0.415, passed: false, elapsedMs: 812,
      tag: null, hasOverrides: false,
      replaySeeds: [17],
      file: "mirror_warrior.json" },
    ...
  ],
  tags: ["archer-range-3"]
};
```

세트 파일(`scenarios/all.json`)을 돌릴 때마다 갱신한다. 단일 시나리오 실행 시에는 해당 항목만 갱신하고
나머지는 보존한다(기존 항목을 날리면 매트릭스가 비어 버린다).

**같은 시나리오가 태그별로 여러 항목을 가진다.** `tag: null`인 항목이 정본이고, 태그가 붙은 항목은 실험
결과다. 매트릭스는 기본적으로 정본만 그리고, 비교 모드(§5.4)에서 태그 항목을 정본 위에 겹쳐 보여준다.
항목의 식별자는 `(name, tag)` 쌍이며, 리플레이 키(§4.2)도 같은 쌍을 앞부분에 쓴다.

**결과 파일이 사라진 항목은 갱신 시 인덱스에서 자동으로 뺀다.** 실험 결과를 지웠는데 매트릭스에 유령
행이 남으면 클릭했을 때 "파일이 없다"만 뜨고, 그것이 도구 전체의 신뢰를 깎는다.

### 4.5 `file://`에서 열려야 한다

정적 HTML이 `fetch('../results/x.json')`을 하면 로컬에서 CORS로 막힌다. "서버를 띄우라"는 안내는
"쉽게 조절한다"는 목적의 반대다. 그래서 CLI는 **JSON과 함께 `.js` 래퍼를 같이 쓴다.**

- `<script>` 태그는 `file://`에서도 로드되므로 `index.html`을 더블클릭하면 그냥 열린다.
- 리플레이는 무거우므로 `<script>` 동적 주입으로 필요할 때만 불러온다.
- 같은 파일이 GitHub Pages에도 그대로 올라간다. 배포용 별도 빌드가 없다.
- 기존 `.json` 출력은 유지한다 — `BalanceLabCrossCheckTests`가 읽고 있고, 사람이 직접 읽기에도 그쪽이 낫다.

## 5. 뷰어

세 화면 한 페이지(해시 라우팅), **의존성 0의 바닐라 JS 단일 파일**. 빌드 스텝 없음.
잼 일정 · `file://` 직접 열기 · 심사자가 소스를 그대로 읽는다는 세 조건이 모두 같은 답을 가리킨다.

### 5.1 화면 1 — 매트릭스 (진입)

- 상단: 요약 카드 4개(시나리오 수 / 통과 / 이탈 / 총 판수), 생성 시각, 오버라이드 적용 배지
- 필터: 밴드별, "이탈만 보기"
- 본문: 시나리오 행 목록

**승률 바의 문법이 이 화면의 핵심이다.** 배경 띠 = `bands.json`의 목표 구간, 세로선 = 실측 승률.
이 도구의 언어가 "밴드"이므로 화면의 기본 좌표계도 밴드여야 한다. 숫자 71.5%를 읽고 머릿속에서
65~75와 비교하는 단계를 없애는 것이 목적이다.

판정은 색만으로 표시하지 않는다 — 아이콘 + "통과/이탈" 라벨을 함께 붙인다.

### 5.2 화면 2 — 시나리오 상세

- **종료 틱 분포 히스토그램.** 밴드가 못 잡는 문제를 잡는다. 승률 50%인데 분포가 쌍봉이면 그건 "균형"이
  아니라 "선공 결정론"이다.
- **시드 그리드.** 200판을 200칸으로 편다. 칸 색 = 승자. 이것만으로 "박빙인데 한쪽으로 쏠린 판"이 보인다.
- **분대 요약 패널.** 좌/우 평균 생존자, 장군 생존율, 액티브 평균 발동 수 (전부 기존 `SquadRecord`에 있다).

**시드 직접 입력** — 그리드 옆에 시드 번호 입력란을 둔다. 입력 후 Enter 시 세 갈래로 분기한다:

| 상황 | 동작 |
|---|---|
| 리플레이가 덤프된 시드 | 리플레이 뷰어로 이동 |
| `runs` 범위 안이지만 미덤프 | 해당 시드의 기록(승자 · 종료 틱 · 분대별 생존)을 인라인으로 펼치고, 그 시드를 덤프하는 CLI 명령을 복사 버튼과 함께 제시 |
| `runs` 범위 밖 | "이 시나리오는 0~199까지 돌았다"고 알리고, 범위를 넓혀 재실행하는 명령을 제시 |

그리드 클릭도 같은 분기를 탄다. 즉 그리드는 시드 입력의 시각적 단축키이고, 입력란은 200칸을 눈으로 찾지
않아도 되는 정확한 경로다. 미덤프 시드를 "없음"이 아니라 **"한 줄 실행하면 생김"** 으로 제시하는 것이
이 화면의 설계 의도다.

### 5.3 화면 3 — 리플레이 뷰어 + 튜닝 패널

**좌: 재생 영역**

- 탑다운 2D 캔버스. 아레나 60×40 → 3:2 비율
- 유닛 = 점. 팀으로 색, 장군은 크기로 구분(기획 §4의 "장군은 크기로 즉시 구분" 규칙과 동일한 언어)
- HP는 점의 불투명도
- 컨트롤: 재생/일시정지 · 타임라인 스크럽 · 배속(0.25x~4x) · 프레임 단위 스텝
- 타임라인 위에 이벤트 마커(장군 액티브 · 스킬 · 분대 전멸)
- 하단: 팀별 실시간 생존 수, 현재 틱

**우: 튜닝 패널**

- 기준선은 `results/assets.js`가 공급한다. 브라우저는 `.asset`(YAML)을 읽을 수 없으므로 CLI가
  **오버라이드 적용 전** 수치를 스냅샷으로 내보낸다 — 이 "적용 전"이 계약이다. 태그 실행을 보고 있어도
  슬라이더의 0점은 언제나 정본 `.asset`이라야 내보낸 패치가 정본 대비 최소가 된다.
- 슬라이더는 그 기준선에서 **델타만 축적**한다. 값을 원래대로 되돌리면 변경 목록에서 빠진다.
- 여는 것은 **이 판에 실제로 등장하는 롤**뿐이다. 5개 롤을 전부 나열하면 패널이 무관한 슬라이더로 덮인다.
- enum(이동 패턴·타겟팅)과 리스트 필드는 슬라이더로 열지 않는다 — 구조 변경은 `.asset`의 몫이고,
  리스트는 오버라이드 자체가 거절한다.
- 변경된 필드 수를 항상 표시한다.
- 「overrides.json 내보내기」는 파일 다운로드 + **실행 명령을 함께 클립보드에 복사**한다:

```
dotnet run --project Tools/BalanceLab -- Tools/BalanceLab/scenarios/all.json --overrides Tools/BalanceLab/tuning/archer-range-3.json --tag archer-range-3 --replay 17
```

### 5.4 비교 모드

`--tag`가 붙은 결과가 존재하면 매트릭스가 **정본 대비 델타**를 함께 표시한다 (`71.5% → 68.2% ▼3.3`).

밸런싱에서 알고 싶은 것은 절대값이 아니라 "내가 방금 만진 것이 무엇을 움직였나"다. `index.js`가 태그
목록만 들고 있으면 되므로 구현 비용은 거의 0인데 효용이 가장 크다.

## 6. 검증

리플레이 기능의 유일한 실질적 위험은 **관측이 대상을 바꾸는 것**이다. 두 개의 값싼 불변식으로 막는다.

1. **덤프 온/오프 회귀** — 같은 시드를 `--replay` 있이/없이 실행해 승자와 종료 틱이 완전히 일치해야 한다.
   기존 "시드 0 = 339틱" 회귀 관행에 한 줄 추가하는 수준이다.
2. **자기 교차 검증** — 리플레이 마지막 프레임의 팀별 생존자 수가 `results` JSON의 `survivors` 합계와
   일치해야 한다. 덤프 시점에 CLI가 스스로 assert한다. 불일치는 샘플링/양자화가 깨졌다는 뜻이다.

추가로:

3. **no-op 오버라이드 경고** — 패치하려는 값이 `.asset` 원래 값과 같으면 그 필드를 경고로 알린다.
   "적용됐는데 아무것도 안 바뀐" 상황을 잡되, 비용이 0이다. (설계 초안은 오버라이드 유/무 두 번
   실행해 비교하는 안이었으나, 14시나리오 × 200판을 두 배로 돌리는 값을 하지 않는다 — 덮으려던
   실패 모드는 값 비교만으로 대부분 잡힌다.)
4. **`BalanceLabCrossCheckTests` 유지** — §2 참조. 기존 계약 그대로.

### 실패 처리

전부 **fail-fast + 다음 행동 안내**로 통일한다.

| 상황 | 동작 |
|---|---|
| `index.js` 없음 | 뷰어가 "CLI를 먼저 실행하라" + 실행 명령 표시 |
| 리플레이 파일 없음 | 시드 칸 비활성 + 덤프 명령 제시 (§5.2) |
| 오버라이드 미등록 키 | CLI 즉시 예외 (종료 코드 1) |
| `--overrides`에 `--tag` 누락 | CLI 사용법 오류 (종료 코드 2) |
| 결과와 리플레이의 시나리오/시드 불일치 | 뷰어 상단에 경고 배너 |

## 7. 구현 순서

| 단계 | 내용 | 이 단계만으로 얻는 것 |
|---|---|---|
| 1 | `--overrides` + `appliedOverrides` 기록 + 태그 강제 | Unity 없이 튜닝 가능 |
| 2 | `index.js` 집계 출력 + 매트릭스 화면 | 14개 시나리오가 한눈에 |
| 3 | 시나리오 상세(히스토그램 · 시드 그리드 · 시드 직접 입력) + 비교 모드 | 튜닝 전/후 비교 성립 |
| 4 | `--replay` 레코더 + §6의 두 불변식 | 궤적 데이터 확보 |
| 5 | 리플레이 뷰어 + 튜닝 패널 | 루프 완성 |

1~3단계만으로 독립적으로 쓸모가 있도록 짠 순서다. 일정이 밀리면 4~5를 잘라낼 수 있다.

## 8. 범위 밖 (명시적 YAGNI)

- **로컬 서버 모드(`--serve`)** — 정적 모드와 이중 유지 부담. 정적으로 충분하다.
- **WASM(브라우저에서 시뮬 직접 실행)** — 빌드 파이프라인·용량 리스크가 잼 일정에 맞지 않는다.
- **3D 렌더** — 밸런스 판단에 필요 없다. 3D는 에디터 씬의 몫이다.
- **인게임 디버그 패널** — 제출 빌드에 개발 도구를 넣지 않는다.
- **다크모드 · 모바일 레이아웃** — 개발자가 데스크톱에서 쓰는 도구다.
- **뷰어에서 `.asset` 직접 쓰기** — 정본은 하나여야 하고, 승격에 사람의 손이 들어가는 것이 안전장치다.
- **레벨 스윕** — README의 기존 판단 그대로. `ArmyStatCalculator`를 링크 컴파일로 되살린 뒤의 과제.
